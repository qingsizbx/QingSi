第一部分  先抓住一句话                         【PPT 第 1–3 页】
================================================================

  皮瓣监测只是第一个落地场景；
  我们真正要搭的，是一个可复用的
  "边缘采集 + 云端汇聚 + 实时看板 + AI 分析"监测平台。

为什么要先强调这句话？

  老师给的需求表面上是"做一个让患者上传照片、医生查看照片的小程序"。
  如果只按这个需求做，很容易写成一个"写死了皮瓣业务"的小程序，
  以后想用到烟草在线监测，只能推倒重来。

  而老师的补充说得很清楚：这个系统和工业上的边缘—云监测系统在架构上
  非常相近，希望"一物多用"。所以我们的设计从第一天起就分成两层：

    平台（通用）：不认识"皮瓣"，只认识"监测对象、采样、分析、告警"。
    领域包（专用）：告诉平台"在医疗场景里，监测对象叫患者，
                   每小时采一次，看颜色、纹理、肿胀"。

  后面所有的设计决策，都可以用这句话去检验：
  "这个东西写进平台，烟草场景还能不能直接用？"
  能，就放平台；不能，就放领域包。

一页概览里的四个数字（PPT 第 2 页），可以帮你快速记住整体：

  3 类     用户角色：患者、医护、管理员
  1h→4h    采样频率：术后 72 小时内每小时一次，之后每 4 小时一次
  4 层     技术架构：端、边、云、智
  2 个     应用场景：皮瓣监测 → 烟草在线监测

以及四条关键设计决策：

  1. 一个小程序，三套工作台（按登录角色切换界面）
  2. 平台 + 领域包（场景差异放进配置）
  3. 通用边缘数采端（Windows / Linux 同一套代码）
  4. AI 接口先留好（一期攒数据，二期接模型）

第二部分  我们要解决什么问题                     【PPT 第 4 页】
================================================================

2.1 临床背景（用大白话说）

  皮瓣移植：从身体其他地方取下一块"带着血管的皮肤和皮下组织"，
  移到需要修复的创面上。关键是这块组织要"活下来"——血管要通。

  术后最怕的是"血管危象"：
    - 动脉进不来血（动脉危象）→ 皮瓣发白、发凉
    - 静脉回不去血（静脉危象）→ 皮瓣发紫、肿胀
  发现得晚，皮瓣就会部分或全部坏死。

  所以医护要盯的指标是：
    颜色     苍白 → 动脉供血不足；青紫 → 静脉回流障碍
    纹理     皮纹、皱褶、水疱、表面光泽的变化
    肿胀     肿胀程度和张力，是不是越来越重
    扩展     皮温、毛细血管回流（以后可以接传感器）

  这几项正好也是以后 AI 模型要学的东西。

2.2 监测频率

  以"手术结束时间"为起点 T0：

    T0 ────────────── 72h ──────────────────────>
       每 1 小时一次          每 4 小时一次
       （每天 24 次，共 72 次） （每天 6 次）

  前三天是最关键的窗口期，频率最高。

2.3 现在的痛点（为什么需要这个系统）

  - 夜间人手紧张，护士巡视频次高、负担重
  - 纸质记录分散，很难把今天和昨天的样子放在一起对比
  - 早期变化很细微，判断依赖个人经验
  - 医生不在病房时，没法远程看、远程会诊

  系统要解决的就是三件事：按时采集、远程查看、留档对比。
  再往后一步，是用 AI 帮医生"提前发现"。

第三部分  谁在用这个系统：三类用户               【PPT 第 5 页】
================================================================

  可以把三类用户理解成数据的"生产者、消费者、管理者"：

  ┌ 患者 / 家属 —— 数据提供方
  │   做什么：扫码绑定 → 按提醒拍照上传 → 看自己的记录和下次时间
  │   最在意：操作简单，3 步完成上传（患者刚做完手术，不能复杂）
  │
  ├ 医生 / 护士 —— 数据使用方
  │   做什么：
  │     (1) 查看任一负责患者的全部历史图像（按时间轴前后对比）
  │     (2) 实时监控墙：一屏看全病区所有患者的最新状态
  │     (3) 评估标注、记录处置；接收超时提醒和（以后的）AI 预警
  │   最在意：一眼看出谁有异常
  │
  └ 管理员 —— 系统运维方
      做什么：新增 / 停用用户、分配角色和科室；
              配置采样策略模板；登记数采端设备；看审计日志
      最在意：账号和配置可控、可追溯

  注意两点：
  - 老师提到的医生两大功能——"查看每个患者的历史图像"和
    "像车辆监控系统一样看所有患者的实时信息"——都在医护端里。
  - 角色不写死。以后加"护士长、科研人员"，或者工业场景的
    "质检员、工艺员"，都只是配置一个新角色。

第四部分  系统怎么分层：端 · 边 · 云 · 智        【PPT 第 6–7 页】
================================================================

4.1 先讲六条设计原则（它们决定了后面的分层）

  1. 平台 + 领域包   核心平台与业务解耦，医疗、烟草各是一个可插拔的领域包
  2. 配置驱动       频率、术语、表单、告警规则写成配置，不写死在代码里
  3. 接口先行       先定好接口文档，前端、后端、数采端、AI 四方并行开发
  4. 边云协同       边缘就近采集、缓存、预处理；云端集中存储、调度、展示
  5. 事件驱动       "新图片到了"这样的事件发到消息总线，谁关心谁订阅
  6. 安全合规       医疗影像是敏感个人信息：最小权限、全程加密、操作留痕

4.2 四层分别是什么

  ┌ 端（用户终端）
  │   微信小程序（患者 / 医护 / 管理员三合一）、Web 管理后台、监控大屏
  │   作用：人和系统打交道的地方
  │
  ├ 边（边缘数采端）
  │   装在病区电脑或工厂工控机上的常驻程序，Windows / Linux 都能跑
  │   作用：接摄像头、相机、传感器，就近采集、缓存，断网也不丢数据
  │
  ├ 云（平台服务）
  │   接入层：API 网关、统一鉴权、WebSocket 实时推送、MQTT（预留）
  │   服务层：用户与权限、组织与对象、监测任务、采样排程与提醒、
  │           媒体服务、监控墙、告警规则、审计日志
  │   数据层：PostgreSQL 数据库、Redis 队列、对象存储（存图片）、
  │           时序库（预留，工业数据用）
  │   作用：系统的大脑和仓库
  │
  └ 智（智能层，预留）
      AI 网关 + 各个模型（皮瓣模型、烟草缺陷检测模型、边缘轻量模型）
      作用：看图判断风险，给医生提示

  一个类比帮助记忆：
    端 = 前台窗口，边 = 各地的收货点，云 = 总仓库加调度中心，
    智 = 质检专家。

4.3 用"一张照片的旅程"把四层串起来

  这是汇报时最好用的讲法，按顺序讲一遍，老师就能听懂数据怎么流动：

   ① 到点了，平台的"采样排程"给患者推一条微信提醒
   ② 患者打开小程序，在引导框里对准创面拍照
   ③ 小程序先向平台要一个"上传凭证"
   ④ 照片直接传到对象存储（不经过业务服务器，省带宽）
   ⑤ 小程序告诉平台："我传好了"，平台登记一条"采样记录"
   ⑥ 平台发出事件"新采样到达"（sample.created）
   ⑦ 监控墙收到事件，医生屏幕上这个患者的格子立刻刷新
   ⑧ （二期）AI 网关也收到事件，调用模型打分，超过阈值就告警
   ⑨ 医生点开格子，看历史对比，做出"正常 / 可疑 / 异常"评估

  如果是病区床旁摄像头拍的照片，第 ②–⑤ 步由"边缘数采端"自动完成，
  后面完全一样。这就是"接口统一"的好处。

第五部分  为什么说它和工业监测是一回事：一物多用  【PPT 第 8–9 页】
================================================================

5.1 逐项对照

  架构要素     皮瓣监测（医疗）              烟草在线监测（工业）
  ----------------------------------------------------------------
  监测对象     患者的移植皮瓣                烟支 / 烟包 / 设备工位
  采集端       患者手机、床旁摄像头          产线工业相机、传感器、PLC
  边缘节点     病区护士站电脑                工控机
  采样策略     72h 内每 1h，之后每 4h        按节拍 / 班次 / 批次
  分析模型     颜色·纹理·肿胀 → 坏死风险     外观缺陷·尺寸·色差 → 质量判定
  实时看板     病区患者监控墙                车间中控大屏
  异常处置     通知医生、记录处置            报警、剔除、工艺调整
  组织层级     医院→科室→病区→床位           工厂→车间→产线→工位

  每一行在架构上都是"同一个东西"，只是名字和参数不同。

5.2 通用领域模型：8 个通用概念

  为了让平台"不认识皮瓣"，我们在数据库和代码里只用 8 个通用实体：

  【谁被监测】
    租户 Tenant        医院          /  卷烟厂
    组织 Org           科室、病区     /  车间、产线
    监测对象 Subject   患者皮瓣       /  机台、工位
    监测任务 Task      术后监测周期   /  一个生产批次

  【监测到了什么】
    采集源 Source      手机、摄像头   /  工业相机
    采样 Sample        一张创面照片   /  一帧图像
    分析结果 Inference 坏死风险评分   /  缺陷类型判定
    事件告警 Alert     疑似血管危象   /  质量异常报警

  那"皮瓣部位、手术方式"这些医疗特有的信息放哪？
  放在每条记录的"扩展属性"里（PostgreSQL 的 JSONB 字段），
  由领域包里的"表单定义"描述有哪些字段。
  好处：换到烟草场景不用改数据库表结构。

5.3 领域包里装什么

  术语字典      界面上显示"患者"还是"工位"
  表单定义      建档时要填哪些字段
  采样策略      多久采一次
  告警规则      什么情况算异常
  AI 模型绑定   用哪个模型分析
  大屏模板      监控墙长什么样

  所以"换场景"主要就是"写一个新的领域包"。
  PPT 上写的"目标复用率 ≥ 80%"是我们给自己定的目标，用来约束开发时
  不要把业务写死进平台，不是测算出来的数字。汇报时请这样说明。

第六部分  关键模块逐个讲                     【PPT 第 10–16 页】
================================================================

6.1 用户端：一个小程序，三套工作台           【第 10 页】

  为什么不做三个小程序？
    维护三套代码、审核三次、用户还要分清装哪个，成本高。
    做成一个，登录后按角色进入不同"工作台"就行。

  三套工作台的页面：
    患者端：首页（下次上传倒计时）、拍照上传、我的记录、消息
    医护端：监控墙（首页）、患者列表、患者详情、评估标注
    管理端：用户管理、组织与床位、采样策略、设备与审计

  登录与绑定（这个流程要讲清楚）：
    - 医护：管理员先在后台建好账号 → 医护第一次用微信登录时绑定
    - 患者：护士建档后出示一个二维码 → 患者微信扫码就绑定到自己的病例
    这样患者不用注册、不用记账号密码。

  一个原则：前端按角色隐藏菜单只是为了好用，
  真正的权限判断一定在后端做，防止有人绕过界面直接调接口。

6.2 权限模型：角色 + 数据范围                 【第 11 页】

  两个问题分开管：
    角色决定"能做什么"（比如能不能评估标注）
    数据范围决定"能看谁的"（比如只能看本科室的患者）

  简化的权限表：
    功能              患者      医护            管理员
    上传图片          本人      代拍上传        —
    查看历史图像      本人      负责/本科室     只读审计
    实时监控墙        —         本科室          全院
    评估标注          —         可以            —
    采样策略配置      —         本科室调整      全局模板
    用户与角色管理    —         —               可以
    数采端设备管理    —         —               可以

  技术上叫 RBAC：把每个操作定义成"权限点"
  （如 sample:upload 上传、wall:view 看监控墙），
  角色就是一组权限点。加角色 = 勾选权限点，不用改代码。

  数据范围分级：本人 → 本组 → 本科室 → 全院；
  工业场景对应：工位 → 产线 → 全厂。

6.3 核心流程：7 步闭环                       【第 12 页】

  1 建档   护士创建监测任务，录入手术结束时间 T0，生成绑定二维码
  2 绑定   患者微信扫码，阅读并同意隐私条款
  3 排程   系统按采样策略自动生成整张上传时间表
  4 提醒   到点推送提醒；超时没传就通知责任护士
  5 上传   引导拍照 → 质量检查 → 压缩并生成缩略图 → 入库
  6 查看   监控墙实时刷新；医生查看、对比、评估
  7 AI     （预留）风险评分，超过阈值自动告警

  这一页最重要的是下面的"数据飞轮"：
    医生评估标注 → 带标签的数据集 → 训练模型 → AI 辅助提示 → 医生复核反馈
  一期虽然没有 AI，但医生每次点"正常 / 可疑 / 异常"，都是在给二期
  攒训练数据。这是"一期就要做评估标注功能"的原因。
  同时要强调：AI 只做辅助提示，诊疗判断始终由医生作出。

6.4 采样策略引擎：频率可配置                  【第 13 页】

  老师给的规则（72h 内每小时、之后每 4 小时）不写死在代码里，
  而是写成一段配置：

    {
      "policy": "FLAP_DEFAULT",
      "anchor": "surgeryEndTime",
      "rules": [
        { "from": "0h",  "to": "72h", "every": "1h" },
        { "from": "72h", "to": "end", "every": "4h" }
      ],
      "graceMinutes": 15,
      "escalate": ["patient", "nurse", "doctor"]
    }

  读法：从手术结束时间算起，0–72 小时每 1 小时一次，之后每 4 小时一次；
  允许前后 15 分钟误差；超时依次提醒患者 → 责任护士 → 主治医生。

  这样做的好处：
    - 医生发现某个患者可疑，可以临时改成每 30 分钟一次
    - 以后规则变了（比如改成 48 小时），改配置就行
    - 工业场景用同一个引擎，按节拍、班次、批次触发采集

  提醒通道要特别注意：
    微信"订阅消息"是一次性授权的——用户同意一次，只能推一条。
    所以设计成：每次上传成功后，引导患者"订阅下一次提醒"；
    如果超时，升级通知护士站；必要时用短信兜底。

  每个采样时间点有状态：待上传 → 临近到期 → 已上传 / 超时。
  这些状态就是监控墙上格子的颜色来源。

6.5 实时监控墙：像车辆监控一样                【第 14 页】

  这是老师特别提到的功能。样子像车辆监控中心的大屏：
  一屏是很多宫格，每个格子是一个在监患者。

  每个格子显示：最新一张照片的缩略图、床号（姓名脱敏，如"12床 张*"）、
  状态颜色、下次上传倒计时。

  状态颜色：
    绿 = 正常
    黄 = 临近上传时间
    红 = 超时未传
    紫 = AI 预警（二期）
  有异常的格子自动排到最前面。

  其他功能：4 / 9 / 16 宫格切换；新图片到达时用 WebSocket 实时推送，
  秒级刷新；点格子进入患者详情看历史对比。

  "实时"分两步走，汇报时要讲清楚：
    一期：准实时"照片墙"——显示的是最新上传的照片，不是视频
    二期：如果接床旁摄像头，升级为真正的实时视频
          （摄像头 RTSP / 国标 GB28181 → 转成浏览器能播的 WebRTC），
          这套流媒体服务和工业视频监控是同一套

6.6 数采端（边缘代理）                        【第 15 页】

  它是"一物多用"的关键部件。是一个装在 Windows 或 Linux 电脑上的
  常驻程序，内部是一条五段的流水线：

    采集驱动 → 预处理 → 本地推理（可选）→ 本地缓存 → 上行通道

    采集驱动   接各种设备：USB 摄像头、网络摄像头、工业相机、
              文件夹监听、PLC / 传感器
    预处理     模糊/曝光检测、去重、压缩、生成缩略图、加时间水印、
              遮挡隐私区域
    本地推理   可选：在本地直接跑 AI 模型，网络不好也能及时预警
    本地缓存   先存在本地，断网了也不丢，网络恢复后自动续传
    上行通道   通过 HTTPS 或 MQTT 上传到云端，带签名鉴权

  反方向还有"远程管理"：设备注册、心跳、配置下发、远程升级、日志回传。

  同一份程序：
    在医院 = 病区护士站电脑 + 床旁摄像头（服务 ICU 或行动不便的患者）
    在工厂 = 产线工控机 + 工业相机 / 传感器
  区别只是装了哪些"驱动插件"。

6.7 AI 预留接口                               【第 16 页】

  一期不做模型，但接口现在就定好，二期直接"插"进来：

    采样入库 → 发出事件 → AI 网关（按场景选模型）→ 模型服务
            → 结果写回 → 规则引擎（决定是否告警、刷新监控墙）

  输入输出格式是通用的：
    输入：哪张图片、什么场景、用哪个模型、上下文（如术后第几小时）
    输出：风险分、风险等级、标签（如"静脉危象"及置信度）、
          指标（颜色、纹理、肿胀各几分）、模型版本
  皮瓣模型和烟草缺陷检测模型用同一个格式。

  两种调用方式：
    轻量模型同步返回；重模型排队、算完回调；
    边缘端也能跑同一个模型（ONNX 格式）。

  一个容易忽略但非常重要的点：
    照片质量决定 AI 的上限。光线、角度、距离不一致，模型就学不好。
    所以一期就要做"拍摄规范"：固定距离和角度、屏幕上的引导框、
    在画面里放一张标准色卡做颜色校正。

第七部分  技术选型：为什么这样选               【PPT 第 17 页】
================================================================

  总原则：按老师要求以 JavaScript 为主线，全栈统一；
  只有 AI 模型用 Python（模型生态都在 Python），通过接口隔开。

  用户端      uni-app（Vue 3）
              一套代码能编译成微信小程序和 H5 网页，
              以后工厂电脑用浏览器也能打开
  后台/大屏   Vue 3 + Element Plus + ECharts
              和小程序同属 Vue 体系，学一套用两处
  业务后端    Node.js 20 + NestJS
              按"模块"组织代码，正好对应我们的模块划分；
              自带"守卫"机制，适合做权限控制
  数采端      Node.js + 驱动插件
              Windows / Linux 同一份代码
  数据库      PostgreSQL
              JSONB 字段适合存领域扩展属性；
              以后加 TimescaleDB 扩展就能存工业时序数据
  队列        Redis + BullMQ
              定时提醒、超时检测、异步任务
  对象存储    MinIO（自己部署）或 腾讯云 COS
              接口兼容，切换不用改代码
  预留        EMQX（MQTT，物联网消息）、ZLMediaKit（视频流）、
              Python + FastAPI + ONNX Runtime（AI 服务）
  工程化      Docker Compose 一键部署、GitHub Actions 自动检查

  说明：NestJS 通常配合 TypeScript 使用，TypeScript 是 JavaScript 的
  "加强版"，可以先用 JS 写，熟悉后再逐步引入。

  audit 审计 · domain-pack 领域包

8.3 接口契约（一期 11 个主要接口）

  认证      POST /api/v1/auth/wx-login             微信登录换令牌
  监测任务  POST /api/v1/tasks                     建档、生成二维码
  绑定      POST /api/v1/tasks/{id}/bind           患者扫码绑定
  上传凭证  POST /api/v1/media/upload-token        拿直传凭证
  采样      POST /api/v1/samples                   登记一次采样
  历史      GET  /api/v1/subjects/{id}/samples     查历史图像
  监控墙    GET  /api/v1/wall + WS /ws/wall        快照 + 实时推送
  评估      POST /api/v1/samples/{id}/reviews      医生评估标注
  用户      POST /api/v1/admin/users               新增用户
  设备      POST /api/v1/edge/heartbeat            数采端心跳
  AI 结果   POST /api/v1/inferences                AI 结果回写（预留）

  预留的事件：sample.created（新采样）、task.overdue（超时）、
  inference.done（分析完成）、alert.raised（产生告警）。

  "接口先行"的意思是：评审通过后先把这些接口写成文档（OpenAPI），
  前端和后端都照着文档开发，互不等待。

              （项目负责人：方向、需求确认、验收）

     算法同学（二期引入）               临床顾问（合作医生 / 护士）

                          │
            ┌─────────────┴─────────────┐
            │                           │
      开发 A：前端与交互            开发 B：后端与平台
      - 小程序三端                  - 核心服务、数据库、接口契约
      - 监控墙、后台、大屏          - 采样排程、提醒、权限、审计

      - 前端联调与体验测试          - 部署运维、CI、安全

      双人共同：需求评审 · 代码互审 · 交叉测试 · 文档维护

  （虚线表示协作关系，实线表示汇报关系）

  可以记成"1 + 2 + 2"：
    1 位指导老师把方向；
    2 位开发者按前端 / 后端切分；
    2 类外部支持：临床顾问（现在就需要）、算法同学（二期再引入）。

  两个开发者之间的"边界"就是接口契约：
    A 不需要知道数据库怎么设计，B 不需要知道页面怎么画，
    双方只对接口文档负责。这是两个人能并行开发的前提。

  注：A 负责前端、B 负责后端是建议分工，你们可以按各自擅长调整。

9.2 分工矩阵（每项工作只有一个主责人）

  工作项                  主责        协作        评审
  需求梳理与原型          开发 A      临床顾问    指导老师
  接口契约                开发 B      开发 A      双人互审
  小程序三端 · 监控墙     开发 A      开发 B      临床顾问
  后端服务 · 数据库       开发 B      开发 A      指导老师
  数采端 · AI 接口预留    开发 B      开发 A      指导老师
  拍摄规范 · 评估标准     临床顾问    开发 A      指导老师
  测试 · 部署 · 文档      双人        —           指导老师
  阶段验收                指导老师    双人        —

  主责 = 对结果负责；协作 = 参与实现；评审 = 把关验收。
  "只有一个主责人"是为了避免两个人都管、最后等于没人管。

9.3 协作规范

  Git 流程    每个功能开一个分支，通过 Pull Request 互相审代码后再合并
  迭代节奏    两周一个迭代，每周一次例会（进度、风险、下周计划）
  文档先行    接口要变，先改文档，再改代码
  质量门禁    统一代码风格（ESLint + Prettier），核心模块写单元测试，
              提交后自动检查（CI）
  任务管理    用 GitHub Issues / Projects 看板跟踪

第十一部分  风险与应对                         【PPT 第 20、25 页】
================================================================

  高  小程序医疗类目需要资质；实时音视频组件只对部分类目开放
      → 课题期先用体验版小范围使用；正式上线由医院作为主体申请类目；
        实时视频先放在 Web 端
  中  订阅消息需要用户逐次授权，提醒可能漏发
      → 每次上传后引导订阅下次；超时升级到护士站；短信兜底
  高  照片光照、角度、距离不一致
      → 引导框 + 标准色卡 + 自动质量检测
  高  敏感数据泄露
      → 权限隔离、加密、审计；伦理审批和知情同意
  中  两人团队人力有限
      → 严控一期范围；接口先行并行开发；多用成熟组件
  中  需求变化、跨场景扩展
      → 领域包 + 配置驱动，把变化收在配置层

  数据安全的四道防线（第 20 页）：
    合规前置    医疗健康信息属敏感个人信息，要单独同意；
                配置小程序隐私保护指引；数据境内存储；伦理审批
    访问控制    最小权限、数据范围隔离；图片私有，只发短时效链接；
                查看页面加水印
    传输存储    全程 HTTPS；存储加密；姓名、手机号脱敏；
                拍照引导只拍创面，不拍面部
    审计留存    查看、下载、导出、改权限全部留记录；定期备份

  提醒：小程序类目、订阅消息、音视频组件的具体开放范围，
  以微信官方最新规则为准，立项前需要再核实一次。

第十二部分  汇报指南与老师可能问的问题
================================================================

12.1 汇报节奏建议（约 25–30 分钟）

  开场 2 分钟    讲第一部分那句话：平台 + 领域包，一物多用
  背景 3 分钟    血管危象、72 小时窗口、痛点
  架构 8 分钟    四层架构 + "一张照片的旅程" + 医疗/工业对照表
  模块 8 分钟    重点讲监控墙、采样策略、数据飞轮，其他快速过
  工程 3 分钟    技术选型和仓库结构，点到为止
  组织 4 分钟    组织结构图、分工矩阵、路线图
  收尾 2 分钟    请老师确认 5 件事

  讲的时候抓住三个"亮点"：
    1. 一物多用：医疗和工业逐项对照，老师最关心
    2. 监控墙：老师亲口提的需求，要讲清楚"一期照片墙、二期视频"
    3. 数据飞轮：AI 一期不做，但一期就在为它攒数据

12.2 老师可能问的问题（参考回答）

  问：为什么不做三个小程序？
  答：一个小程序按角色切换界面，只需维护一套代码、审核一次；
      权限由后端统一控制，安全性不受影响。

  问：监控墙是视频吗？
  答：一期是准实时照片墙，显示每个患者最新上传的照片和状态，
      新照片到达秒级刷新；二期如果接床旁摄像头，再升级为实时视频，
      流媒体部分和工业视频监控共用。

  问：患者忘了拍、不会拍怎么办？
  答：到点推送提醒，超时自动升级通知责任护士；拍照页有引导框，
      并自动检测模糊和曝光；行动不便的患者可以由护士代拍，
      或用床旁摄像头经数采端自动采集。

  问：AI 现在不做，先留接口有什么意义？
  答：一是接口和数据格式定好，二期直接接入不返工；二是一期医生的
      每次评估都会存成标注，等于在为模型准备训练数据；三是一期就
      规范拍摄（引导框、色卡），保证数据质量。

  问：具体怎么复用到烟草在线监测？
  答：平台用的是"监测对象、采样、分析、告警"这类通用概念，不写死
      医疗业务。换场景时写一个新的领域包（术语、表单、采样策略、
      告警规则、模型、大屏模板），数采端换上工业相机驱动即可。

  问：为什么用 Node.js，不用 Java？
  答：老师要求主体用 JavaScript；前后端同一种语言，两个人可以互相
      支援、共享代码；NestJS 的模块化结构也适合我们"平台 + 插件"
      的设计。

  问：数据安全怎么保证？
  答：四道防线——合规前置、访问控制、加密传输存储、全程审计；
      图片不公开，只发短时效链接；正式使用可以部署在医院内网。

  问：两个人 8 周做得完吗？
  答：一期只做核心闭环（建档、上传、查看、监控墙、提醒、管理），
      AI 和实时视频都放二期；接口先行让两人并行；尽量用成熟组件。
      8 周是估计值，会根据实际情况调整。

12.3 需要老师当场确认的 5 件事

  1. 小程序用谁的主体注册（个人 / 学校 / 医院），怎么上线
  2. 试点科室、床位规模、参与的医护人数
  3. 一期是否需要床旁摄像头，还是只用患者手机拍照
  4. 数据放公有云，还是医院内网
  5. 伦理审批和患者知情同意由谁牵头

  前两件决定一期范围，第 1、4 件决定部署方式。

12.4 评审通过后两周内的下一步

  - 冻结一期范围和验收标准
  - 输出交互原型和接口文档（OpenAPI v1）
  - 搭好代码仓库、开发环境和自动检查（CI）
  - 和临床顾问确定拍摄规范与评估量表

附录  术语表
================================================================

  边缘 / 边缘计算   在数据产生的地方（病房、车间）就近处理数据，
                    而不是全部传到远处的服务器
  数采端            数据采集端，本项目中指装在本地电脑上的边缘程序
  领域包            把某个行业场景的差异（术语、表单、规则、模型等）
                    打包成的一组配置
  RBAC              基于角色的访问控制：给角色分配权限，再给人分配角色
  OpenAPI           描述接口的标准文档格式，前后端照着它开发
  Monorepo          一个代码仓库里管理多个子项目
  JSONB             PostgreSQL 的一种字段类型，可以灵活存结构不固定的数据
  WebSocket         浏览器和服务器之间的长连接，服务器能主动推消息，
                    用于监控墙实时刷新
  MQTT              物联网常用的轻量消息协议，适合大量设备上报数据
  RTSP / GB28181    摄像头视频流协议；GB28181 是国内视频监控的国家标准
  WebRTC            浏览器里播放低延迟实时视频的技术
  ONNX              一种通用的 AI 模型格式，同一个模型能在云端和边缘运行
  OTA               远程升级：不用到现场，通过网络更新设备上的程序
  CI                持续集成：代码提交后自动检查、自动测试
  MVP               最小可用产品：先做出能用的核心功能，再逐步完善
  对象存储          专门存图片、视频这类文件的存储服务
